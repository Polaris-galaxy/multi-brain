# 双机器人通信协同研发路线图

> 当前范围：两个机器人在执行共同任务时，互相交流进度、目标状态、环境异常、机器人自身异常和协作请求。首版采用显式消息协议、任务状态机和确定性协调；不以端到端多智能体强化学习作为起点。

> 通信基线：**ROS Noetic（ROS1）**。ROS Noetic 已于 2025-05-31 结束官方支持（EOL）；使用它意味着团队需自行承担安全补丁、依赖归档、镜像固定和后续迁移责任。不得把 ROS2/DDS 的 QoS、Lifecycle 或可靠性语义套用到 ROS1。

> 架构基线：首版采用**车队任务协调器/监督器 + 机器人本地安全自治**。中央汇总经过时间戳、质量和版本校验的状态摘要，分配任务并管理排他资源；机器人本地保留急停、避碰、限速、局部规划和命令否决权。不得称为“最高决策者”，因为该表述会错误暗示中央掌握完整实时状态、可越过本地安全且不存在单点故障。

## 1. 目标、原则与边界

### 目标

- [ ] 两个机器人能够共享任务进度、当前位置、剩余工作和预计完成状态。
- [ ] 机器人能够报告环境、目标、设备、通信和任务逻辑异常。
- [ ] 接收方能够判断消息是否新鲜、可信、相关，并触发确认、复查、重规划或任务交接。
- [ ] 车队任务协调器能够基于一致快照分配任务、管理排他资源并下发有时限的任务意图。
- [ ] 每个机器人能够校验、拒绝或安全降级中央命令，而不是无条件执行。
- [ ] 在延迟、丢包、重复、乱序和单机器人故障下保持可预测行为。
- [ ] 所有关键决策可审计、可回放、可复现实验。
- [ ] 后续能够在固定协议上扩展任务分配、共享感知和学习型通信。

### 核心原则

- [ ] **安全本地闭环：** 急停、避障、限速和地理围栏不得依赖远端消息。
- [ ] **事件与状态分离：** 异常事件用于快速通知，周期状态快照用于恢复一致。
- [ ] **进度可验证：** 不只发送百分比，还发送任务状态、证据和剩余工作。
- [ ] **消息幂等：** 重复消息不能重复执行危险动作。
- [ ] **过期失效：** 陈旧位置、目标或异常不得继续影响决策。
- [ ] **冲突显式化：** 两机器人判断不一致时不得静默覆盖。
- [ ] **通信有代价：** 只有消息带来的决策价值超过带宽、延迟和能耗成本时才值得发送。
- [ ] **中央权限有限：** 中央拥有任务级协调权，不拥有电机级控制权或本地安全覆盖权。
- [ ] **命令带租约：** 任务和排他资源只有在有效epoch与租约内才生效，过期自动失权。

### 当前不作出的承诺

- [ ] 不声称通信越多，协作越好。
- [ ] 不把训练期集中信息等同于运行时通信。
- [ ] 不让学习策略绕过底层安全控制。
- [ ] 不在仿真链路理想时宣称真机通信可靠。
- [ ] 不在两机器人任务尚未稳定前扩展到大规模机器人群。
- [ ] 不把集中式调度本身包装为算法创新。
- [ ] 首版不实现热备核心或多核心选主。

## 2. 系统分层架构

### 2.1 ROS1部署基线

首版采用两个机器人共享一个 `roscore`：

- [ ] 在固定主机或其中一台机器人上运行 `roscore`。
- [ ] 两机器人统一配置 `ROS_MASTER_URI`。
- [ ] 每台机器人正确配置可被对方访问的 `ROS_IP` 或 `ROS_HOSTNAME`。
- [ ] 使用 `/robot_1`、`/robot_2` 命名空间隔离同名节点、topic、service 和参数。
- [ ] 使用 `roscpp` 实现高频、低延迟或安全相关节点；`rospy` 适合编排、监控和非实时工具。
- [ ] 使用 topics 传递状态和事件，services 执行短时查询/命令，`actionlib` 执行可反馈、可取消的任务交接。
- [ ] 使用 `diagnostic_msgs`/`diagnostic_updater` 发布健康状态。
- [ ] 使用 `bond` 或显式 heartbeat topic 检测节点和机器人失联。
- [ ] 使用 `rosbag` 录制和回放，不使用 `rosbag2`。
- [ ] 使用 `dynamic_reconfigure` 调整允许在线修改的阈值，并记录每次变更。

#### 单 `roscore` 风险

- [ ] `roscore`/ROS Master 是名称注册、发现和参数服务器的单点故障。
- [ ] Master失效后，既有TCPROS连接可能暂时继续，但新节点注册、重新发现、service查询和参数访问会失败；不得依赖其必然持续。
- [ ] Master所在机器人掉电或网络隔离时，协作能力可能无法恢复。
- [ ] 首版接受该限制，但必须测试Master进程退出、主机掉线和恢复。
- [ ] 本地安全、局部规划和急停不得依赖Master在线。

#### EOL工程控制

- [ ] 固定Ubuntu 20.04/Noetic、系统包和工作空间依赖版本。
- [ ] 建立可复现容器或系统镜像及内部包缓存。
- [ ] 限制ROS网络暴露范围；ROS1默认不提供现代安全与身份认证能力。
- [ ] 维护内部漏洞和补丁清单。
- [ ] 将迁移ROS2或替代中间件列为独立技术债，不虚构上游继续维护。

### 2.2 车队任务协调器/监督器

首版在固定主机上运行一个逻辑主核心。它可以与`roscore`同机部署，但两者职责不同：ROS Master负责发现与注册，车队监督器负责业务协调。

```text
robot_1 state ─┐
               ├→ 状态聚合器 → FleetSnapshot → 任务分配/资源预约
robot_2 state ─┘                                  ↓
                                           带租约TaskCommand
                                                   ↓
                           本地command_gate → 本地执行器 → 本地安全层
```

中央核心应负责：

- [ ] 聚合机器人状态摘要，标注新鲜度、质量、来源、`boot_id`和`seq`。
- [ ] 生成带`snapshot_id`的一致车队快照；缺失数据记为`UNKNOWN`，不得默认为正常。
- [ ] 接收任务目标、优先级、地图/资源约束和人工暂停/恢复指令。
- [ ] 任务分解、两机器人角色分配、排他资源预约和全局冲突检测。
- [ ] 下发任务级目标、取消、等待、返航或模式请求，并审计决策依据。
- [ ] 在状态陈旧、机器人异常、核心重启或网络分区时执行确定性降级。

中央核心不得负责：

- [ ] 直接发布底盘`cmd_vel`、电机电流、机械臂关节实时指令。
- [ ] 覆盖急停、碰撞规避、速度/地理围栏或设备保护。
- [ ] 替代本地里程计、定位、控制回路和动态障碍即时反应。
- [ ] 依据未经时间、坐标系、协方差和版本校验的“全量状态”决策。
- [ ] 要求机器人在命令过期、核心失联或本地安全条件不满足时继续执行。

### 2.3 单机器人本地层

每个机器人独立具备：

- [ ] 感知与目标检测。
- [ ] 定位、地图和坐标变换。
- [ ] 局部任务状态机。
- [ ] 局部路径规划与控制。
- [ ] 碰撞、急停、限速和地理围栏。
- [ ] 设备健康监测。
- [ ] 异常检测和置信度估计。
- [ ] 通信失联时的降级策略。
- [ ] `command_gate`：校验`epoch`、`command_id`、`valid_until`、前置条件和资源租约，并按幂等语义接收、拒绝或复用结果。
- [ ] `safety_supervisor/cmd_vel_mux`：对中央和本地执行器拥有最终否决权。

### 2.4 通信中间层

- [ ] 消息编码、版本和校验。
- [ ] ROS1 publisher/subscriber队列、TCPROS/UDPROS选择和应用层优先级。
- [ ] 确认、重试、去重和乱序处理。
- [ ] TTL和陈旧消息过滤。
- [ ] 心跳和链路质量估计。
- [ ] 带宽限制和消息节流。
- [ ] 日志、录包和确定性回放。

ROS1 topics没有ROS2/DDS式QoS契约：

- [ ] 默认TCPROS只提供字节流传输基础，不代表业务消息已被接收方处理。
- [ ] 关键事件必须使用应用层ACK、`seq`、TTL、重试和去重。
- [ ] 高频状态使用小`queue_size`，允许新状态替代旧状态。
- [ ] latched topic只用于“最新快照/静态配置”，不得充当可靠事件日志。
- [ ] services不用于长时间任务；任务交接使用`actionlib`。

### 2.5 中央共享协作层

- [ ] 共享任务表。
- [ ] 共享世界模型或地图增量。
- [ ] 目标观测与状态融合。
- [ ] 异常登记、确认、升级和关闭。
- [ ] 任务认领、交接和冲突解决。
- [ ] 协作决策和重规划。
- [ ] 当前核心`epoch`、命令结果、任务租约和排他资源租约。

### 2.6 可选学习层

仅在确定性基线稳定后考虑：

- [ ] 学习“何时发送”。
- [ ] 学习消息压缩或摘要。
- [ ] 学习异常优先级。
- [ ] 学习任务交接收益。
- [ ] CTDE训练、分散执行。

学习层不得替换本地安全层和协议一致性层。

## 3. 统一消息协议

### 3.1 消息信封

所有消息至少包含：

```text
protocol_version
message_id
mission_id
sender_robot_id
recipient_robot_id | broadcast
message_type
severity
sequence_number
sender_timestamp
valid_until
coordinate_frame
pose_reference
confidence
requires_ack
correlation_id
payload
checksum_or_signature
```

### 3.2 通用要求

- [ ] `message_id` 全局唯一，用于去重。
- [ ] `sequence_number` 用于检测乱序和缺失。
- [ ] `valid_until` 明确消息过期时间。
- [ ] 所有空间信息必须声明坐标系和时间。
- [ ] `confidence` 不能替代证据和质量字段。
- [ ] 关键消息必须有 `requires_ack`。
- [ ] 响应消息通过 `correlation_id` 关联原事件。
- [ ] 协议必须版本化并具有向后兼容策略。
- [ ] 不把TCPROS连接成功当成业务处理成功。
- [ ] 关键消息ACK必须由接收方应用节点在校验和落库/入状态机后产生。
- [ ] 发送方按消息ID重试，接收方按消息ID幂等去重。

### 3.3 状态摘要与车队快照

每个机器人周期发布的状态摘要至少包含：

```text
robot_id
boot_id
seq
source_timestamp
receive_timestamp
pose / twist / covariance / frame_id
localization_quality
battery_and_device_health
operating_mode
current_command_id / task_state
local_safety_state
map_version
network_quality
```

- [ ] `boot_id`每次机器人进程/整机启动时改变，防止重启后旧`seq`被误判为新数据。
- [ ] `seq`只在同一`boot_id`内单调增加；乱序或重复状态不更新当前快照。
- [ ] 状态超时使用接收机单调时钟判断；发送时间只在chrony/NTP同步质量合格时用于跨机器人对齐。
- [ ] 状态聚合器按共同截止时刻构造`FleetSnapshot`，记录`snapshot_id`、各状态年龄和外推不确定性。
- [ ] 示例初值：状态10 Hz；`age≤0.5 s`为新鲜、`0.5–1.5 s`为降级、`>1.5 s`为陈旧、`>3 s`为失联。阈值必须按机器人制动距离和网络实测重新标定。
- [ ] 依赖精确相对位置的协调不得使用陈旧状态；可降级为独立区域任务或安全等待。

### 3.4 任务命令、epoch与租约

中央下发的是声明式任务意图，不是低层动作流。任务命令至少包含：

```text
epoch
command_id
mission_id / task_id
target_robot_id
snapshot_id
issued_at / not_before / valid_until / lease_duration
task_type / parameters
preconditions
resource_lease_ids
priority
supersedes_command_id
partition_policy
```

- [ ] `epoch`是核心领导任期/重启代次；核心每次启动从持久化计数器原子递增。
- [ ] 机器人只接受不低于已持久化最高值的`epoch`，低epoch命令一律拒绝。
- [ ] `command_id`全局唯一；相同ID重复到达只返回既有ACK/结果，不重复产生副作用。
- [ ] `valid_until`定义任务租约；机器人仅在租约有效且本地安全允许时执行。
- [ ] 机器人以“校正后的`valid_until`”与“本地接收单调时钟 + `lease_duration`”中更早者作为保守到期时刻；时钟同步质量不足时不得延长租约。
- [ ] 排他资源租约与任务租约绑定；中央不得在旧租约到期加最大时钟偏差/网络裕量前把同一资源重新分配。
- [ ] 命令topic不得latched；关键生命周期可用`actionlib`，但Goal中仍需包含上述fencing字段。
- [ ] 本地ACK至少区分`ACCEPTED`、`REJECTED`、`DUPLICATE`、`STALE_EPOCH`、`EXPIRED`、`COMPLETED`和原因码。

## 4. 消息类型与异常分类

### 4.1 进度与任务消息

- [ ] `HEARTBEAT`：在线状态、时间和链路摘要。
- [ ] `ROBOT_STATUS`：位置、电量、模式、当前任务和健康状态。
- [ ] `TASK_CLAIM`：认领任务。
- [ ] `TASK_PROGRESS`：阶段、已完成量、剩余量和阻塞原因。
- [ ] `TASK_BLOCKED`：任务无法继续。
- [ ] `TASK_HANDOFF_REQUEST`：请求交接。
- [ ] `TASK_HANDOFF_ACCEPT/REJECT`：接受或拒绝交接。
- [ ] `TASK_COMPLETE`：完成及证据。
- [ ] `TASK_ABORT`：终止原因和现场状态。

### 4.2 环境异常

- [ ] 新障碍或通道封闭。
- [ ] 地形、坡度、积水、烟尘、光照或天气异常。
- [ ] 地图与真实环境不一致。
- [ ] 定位地标丢失或环境变化。
- [ ] 人员、车辆或其他动态体进入。
- [ ] 危险区域、坠落边缘或地理围栏风险。

### 4.3 目标异常

- [ ] 目标未发现。
- [ ] 目标位置变化或丢失。
- [ ] 目标类别不确定。
- [ ] 目标重复、冲突或身份不一致。
- [ ] 目标损坏、遮挡或不可达。
- [ ] 实际目标数量与任务描述不一致。
- [ ] 两机器人对目标状态判断冲突。

### 4.4 机器人自身异常

- [ ] 电量、温度或能耗异常。
- [ ] 传感器故障或数据质量下降。
- [ ] 定位漂移或定位失效。
- [ ] 执行器、底盘或机械臂异常。
- [ ] 算力、存储或进程异常。
- [ ] 机器人被困或无法按计划移动。
- [ ] 安全控制触发。

### 4.5 通信和协作异常

- [ ] 链路中断、延迟过高或丢包。
- [ ] 时钟偏差过大。
- [ ] 消息版本不兼容。
- [ ] 重复、乱序或无法解析的消息。
- [ ] 两机器人同时认领同一排他任务。
- [ ] 共享状态长期不一致。
- [ ] 对方消息可信度或数据完整性异常。

### 4.6 可扩展异常注册

新异常类型必须声明：

- [ ] 唯一类型标识。
- [ ] 严重等级。
- [ ] 触发条件和证据。
- [ ] 消息有效期。
- [ ] 默认响应。
- [ ] 是否需要确认、复查或人工介入。
- [ ] 清除异常的条件。

不得用自由文本替代关键机器决策字段；自由文本只能作为补充说明。

## 5. 严重等级与响应策略

| 等级 | 示例 | 本地动作 | 通信要求 | 对方动作 |
|---|---|---|---|---|
| INFO | 正常进度、非关键发现 | 继续任务 | 可批量/周期发送 | 更新共享状态 |
| WARNING | 目标置信度低、轻微定位漂移 | 降速或复查 | 需要确认 | 评估是否协助 |
| CRITICAL | 通道封闭、机器人被困、目标丢失 | 安全停靠或重规划 | 高优先级、确认和重试 | 重分配或前往复核 |
| EMERGENCY | 碰撞风险、人员闯入、严重设备故障 | 立即本地安全动作 | 最高优先级持续广播 | 本地采取安全动作并通知上层 |

### 响应约束

- [ ] EMERGENCY不得等待对方确认后才执行本地安全动作。
- [ ] CRITICAL消息超时未确认时自动升级或通知上层。
- [ ] WARNING需要配置最大复查次数。
- [ ] INFO消息应合并和节流，避免淹没关键消息。

## 6. 任务与异常状态机

### 6.1 任务状态

```text
UNASSIGNED
CLAIMED
IN_PROGRESS
BLOCKED
HANDOFF_REQUESTED
HANDED_OFF
COMPLETED
ABORTED
```

- [ ] 每次状态转换携带原因、证据和序列号。
- [ ] 同一排他任务只能存在一个由中央签发且未过期的任务/资源租约；并发请求由中央按优先级、代价和机器人ID确定性解决。
- [ ] 本地`command_gate`可以因安全、能力、陈旧epoch或前置条件失败拒绝中央分配。
- [ ] 完成消息必须包含结果或可验证证据。
- [ ] 交接必须明确任务上下文、目标状态和未完成步骤。

### 6.2 异常状态

```text
DETECTED
REPORTED
ACKNOWLEDGED
UNDER_REVIEW
CONFIRMED | REJECTED
MITIGATING
RESOLVED
ESCALATED
```

- [ ] 异常事件不可被新状态快照静默删除。
- [ ] 两机器人冲突判断进入 `UNDER_REVIEW`。
- [ ] 环境异常关闭前需确认地图和规划已更新。
- [ ] 目标异常关闭前需确认目标状态或任务策略已更新。

## 7. 共享状态与冲突处理

### 共享状态

- [ ] 机器人状态和心跳。
- [ ] 任务所有权、进度和依赖。
- [ ] 目标观测、身份、位置和置信度。
- [ ] 环境异常和地图增量。
- [ ] 未确认事件和复查请求。
- [ ] 当前`snapshot_id`、状态新鲜度、核心`epoch`、任务/资源租约和命令结果。

### 合并规则

- [ ] 状态快照按版本、序列号和有效期合并。
- [ ] 目标和环境观测保留来源，不直接覆盖。
- [ ] 坐标变换失败时不融合空间观测。
- [ ] 高置信冲突不得用“最后写入获胜”解决。
- [ ] 对同一目标的冲突观测触发复查或第三方/人工裁决。
- [ ] 共享地图更新保留原始观测和撤销能力。

### 时序、核心重启与网络分区

- [ ] 首版核心循环建议2–5 Hz，机器人状态10 Hz，本地安全20–50 Hz；中央频率不得成为安全反应频率。
- [ ] 机器人按本地单调时钟监测命令租约和核心心跳，不能仅依赖ROS时间倒退/跳变后的差值。
- [ ] 核心重启后递增`epoch`，从机器人状态和持久事件日志重建快照；不得重放旧命令作为“恢复”。
- [ ] 重建完成前只能发`HOLD/STOP`等保守命令，不立即重分配排他资源。
- [ ] 网络分区时，失去核心的机器人按命令内`partition_policy`进入`SAFE_HOLD`、完成最小原子步骤或驶向预定义安全点；任何策略都受本地安全否决。
- [ ] 仍连接核心的机器人不得假设失联机器人已消失；在旧任务/资源租约安全到期前，将其最后位置和资源占用按扩大安全边界处理。
- [ ] 涉及共同搬运、狭窄通道互斥等强耦合任务，任一机器人失联即停止协同动作。

## 8. 通信策略

### 周期通信

- [ ] 低频heartbeat topic或`bond`状态。
- [ ] 机器人状态快照。
- [ ] 任务进度摘要。
- [ ] 未确认关键事件摘要。

### 事件触发通信

- [ ] 状态机发生关键转换。
- [ ] 进度跨越预设里程碑。
- [ ] 目标首次发现、丢失或状态改变。
- [ ] 新异常、严重度升级或异常解除。
- [ ] 路径、地图或任务分配发生显著变化。

### 发送判定

消息发送可按决策价值约束：

\[
\operatorname{send}(m)
=
\mathbf 1
\left[
\mathbb E(\Delta R\mid m)
>
\lambda_b C_{\rm bytes}
+\lambda_d C_{\rm delay}
+\lambda_e C_{\rm energy}
\right].
\]

首版不学习该规则，使用可解释阈值和状态机；P3以后才比较学习型调度。

- [ ] 两机器人地图、时间和坐标系不一致。

- [ ] 重试导致危险动作重复执行。

- [ ] 异常分类无限扩张而缺乏默认响应。
- [ ] 学习通信绕过协议和安全边界。
- [ ] 单`roscore`故障导致新连接、发现、service或参数访问失败。

- [ ] P0协议和回放不稳定：不进入协同决策。

- [ ] P3学习通信不能超过事件触发基线：保留确定性系统。
- [ ] 任何阶段本地安全依赖网络：立即重构。
- [ ] 真机测试无法安全故障注入：保持仿真或硬件在环验证。

## 15. 后续通信拓扑升级边界

只有单`roscore`方案通过P0—P2后，才评估：

### Active-passive备份核心

- [ ] 首版不做热备；先用systemd/`roslaunch respawn`、持久epoch和单核心重启恢复验证故障语义。
- [ ] 后续active-passive必须依赖奇数仲裁节点或外部一致性存储形成quorum；两台核心自身无法在网络分区中可靠判断谁应继续领导。
- [ ] leader必须持有短期`leader lease`，每次任期获得单调递增`epoch`作为fencing token。
- [ ] 机器人只接受当前最高epoch且leader lease有效的命令；旧leader即使恢复网络也不能继续控制。
- [ ] 无quorum时不得签发新任务/资源租约；机器人按现有租约到期并进入本地安全降级。
- [ ] standby复制任务、命令结果和租约日志，但不得发布业务命令；切换后依靠`command_id`幂等恢复。
- [ ] 不允许“双活中央核心”；两个核心同时发布再由机器人“看谁先到”不是容错方案。

### ROS1多主

- [ ] 可评估`multimaster_fkie`等ROS1多主方案。
- [ ] 必须显式定义topic发现、命名冲突、重复转发、时间同步和网络分区恢复。
- [ ] 多主只减少Master单点依赖，不自动解决业务一致性和安全。
- [ ] 不允许两个Master下同一任务被分别认领而无冲突仲裁。
- [ ] 多ROS Master与业务leader选举是两个问题；多主发现不能替代quorum、leader lease和fencing。

### 应用层桥接

- [ ] 每台机器人可运行本地`roscore`，通过专用gateway桥接白名单业务消息。
- [ ] gateway沿用现有消息ID、seq、TTL、ACK、重试和去重语义。
- [ ] 只桥接任务、异常、目标和必要地图增量，不透明复制整个ROS图。
- [ ] 桥接传输可使用专用TCP、ZeroMQ、gRPC或其他受控通道，选型需单独验证。
- [ ] 应用层桥接不得改变本地安全回退。

### ROS2迁移

- [ ] 若需要长期维护、安全、复杂QoS或更大规模部署，应单独评估ROS2迁移。
- [ ] ROS1到ROS2迁移属于平台升级，不与当前P0—P3算法验证混在同一阶段。

### 分布式/分层升级

- [ ] 机器人数量、网络分区频率或中央带宽成为瓶颈后，再将任务分配升级为CBBA/C-ADMM等分布式方法。
- [ ] 编队、避碰和相对控制优先保持本地/邻居闭环，中央只发布队形参考和任务约束。
- [ ] 可按区域设置子协调器，但跨区域排他资源仍需明确唯一租约权威。
- [ ] 无论升级为备份核心还是分布式任务分配，本地安全否决权、命令幂等和租约过期语义保持不变。
