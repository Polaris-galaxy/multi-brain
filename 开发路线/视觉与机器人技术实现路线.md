# 视觉多专家与双机器人协同：技术实现路线

> 本文把两份研发路线进一步落实为可编码、可集成、可测试的技术方案。推荐技术栈可替换，但接口、验证门槛和安全边界应保持。

## 1. 总体实施原则

- [ ] 两个系统分别开发、独立验收，再通过稳定接口集成。
- [ ] 视觉系统负责产生目标证据、质量、不确定性和拒识结果。
- [ ] 机器人系统负责通信、任务状态、异常处置、重规划和本地安全。
- [ ] 视觉置信度不能直接触发机器人危险动作。
- [ ] 机器人之间不传递未版本化的任意神经特征。
- [ ] 首版优先确定性协议和可解释融合，学习型模块后置。

# 第一部分：视觉多专家系统

## 2. 推荐技术栈

首版建议：

- [ ] Python。
- [ ] PyTorch作为训练和推理框架。
- [ ] OpenCV/Albumentations用于图像和干预增强。
- [ ] Pydantic或等价强类型方案定义专家接口。
- [ ] YAML配置构建期专家集合、预算和阈值。
- [ ] MLflow、Weights & Biases或等价系统记录实验；只选一种。
- [ ] ONNX Runtime或TensorRT作为后续部署选项，不在P0引入。
- [ ] pytest用于接口、数值约束和回归测试。

不要在首版同时引入多个训练框架、多个配置系统和多个模型注册中心。

## 4. 核心数据结构

```python
@dataclass
class ExpertEvidence:
    protocol_version: str
    expert_id: str
    expert_version: str
    task_id: str
    sample_id: str
    label_space: list[str]
    support: Tensor          # [batch, local_classes], >= 0
    contradiction: Tensor    # [batch, local_classes], >= 0
    uncertainty: Tensor      # [batch], 0..1
    quality: Tensor          # [batch], 0..1
    applicability: Tensor    # [batch], 0..1
    cost: Tensor             # [batch]
    metadata: dict
```

### 强制校验

- [ ] `support`、`contradiction`不得包含负值、NaN或无穷值。
- [ ] 质量、适用性和不确定性限制在 \([0,1]\)。
- [ ] 标签空间和适配器版本必须匹配。
- [ ] 输入缺失时返回显式不可用状态，不伪造零置信度预测。
- [ ] 所有输出携带模型和校准器版本。

### 构建期处理流程

1. [ ] 校验任务标签空间。
2. [ ] 加载主专家及其校准器。
3. [ ] 校验插件协议和版本。
4. [ ] 加载标签适配器。
5. [ ] 检查插件准入报告。
6. [ ] 检查总预算和延迟上限。
7. [ ] 生成不可变运行清单和哈希。

构建期不得根据单个测试样本动态加载未经准入的新插件。

## 7. 运行时推理流程

```text
输入样本
  ↓
主专家推理
  ↓
主专家质量/不确定性评估
  ↓
预算调度：是否调用辅助专家
  ↓
插件证据 → 标签适配 → 独立校准
  ↓
可靠性受限路由
  ↓
有界残差融合
  ↓
冲突检测
  ↓
输出类别 / 弃权 / 请求额外模态
  ↓
审计日志
```

### 受约束融合

\[
L=L_0+\sum_iw_i m_i\tanh(\Delta L_i),
\]

\[
\sum_iw_i\le\eta u_0,
\qquad
w_i\le a_iq_i(1-u_i),
\qquad
\sum_i z_ic_i\le B.
\]

实现时：

- [ ] 约束投影应作为独立函数测试。
- [ ] 路由器输出非法值时使用确定性裁剪并记录告警。
- [ ] 插件异常时权重置零。
- [ ] 所有插件失效时返回主专家结果或弃权。

## 8. 训练流程

### V0：数据和主专家

- [ ] 按样品、批次、设备或上下文域分组拆分。
- [ ] 训练主专家。
- [ ] 固化训练、模型选择、校准和测试集。
- [ ] 建立最佳单模型基线。

### V1：独立插件

- [ ] 单独训练每个插件。
- [ ] 禁止融合损失影响质量专家。
- [ ] 为计量专家使用物理量监督。
- [ ] 生成out-of-fold证据。
- [ ] 计算插件与主专家的Oracle互补增益。

### V2：校准

- [ ] 分别校准主专家和插件。
- [ ] 记录NLL、Brier和风险—覆盖。
- [ ] 校准失败的插件不得进入路由训练。

### V3：路由器

- [ ] 冻结专家。
- [ ] 使用out-of-fold证据训练路由器。
- [ ] 加入插件缺失、过度自信、无关和错误插件扰动。
- [ ] 优化任务损失、最坏域风险和调用成本。

### V4：有限联合微调

- [ ] 只微调标签适配器、残差头和路由器。
- [ ] 使用较小学习率。
- [ ] 每轮重新检查校准和主专家回退。
- [ ] 不默认微调整个专家骨干。

## 9. 毛类纤维实施

### 数据采集

- [ ] 每个原始样品采集多个随机位置和视野。
- [ ] 保存样品、来源、批次、装片、设备和操作者层级。
- [ ] 记录放大倍数和像素—微米标定。
- [ ] 记录曝光、焦点、染色、预处理和图像质量。
- [ ] 训练测试按原始样品或更高层级拆分。

### 第一版专家

1. [ ] `morphology_v1`：显微形态主专家。
2. [ ] `scale_v1`：直径、曲率和鳞片间距插件。
3. [ ] `quality_v1`：对焦、重叠、曝光和标尺质量。

### 后续插件

- [ ] `color_v1`：校准颜色和色素。
- [ ] `spectral_v1`：NIR/FTIR/高光谱。
- [ ] `impurity_v1`：植物、合成纤维和污染。

### 样品级聚合

单根纤维预测不能直接当作样品结论：

```text
视野图像
  → 纤维实例分割
  → 单纤维专家推理
  → 质量过滤
  → 视野内鲁棒聚合
  → 多视野聚合
  → 样品结论和置信区间
```

- [ ] 报告有效纤维数和有效视野数。
- [ ] 使用截尾均值、中位数或鲁棒注意力。
- [ ] 有效样本不足时拒识。
- [ ] 混纺比例使用样品级计数和区间估计。

## 10. 上下文丰富第二场景实施

建议使用 NICO++ 或 Background Challenge：

- [ ] 主专家读取前景对象。
- [ ] 上下文插件读取背景或场景。
- [ ] 质量专家读取遮挡、模糊和裁剪质量。
- [ ] 保持与毛类纤维完全相同的证据结构、路由约束和拒识接口。
- [ ] 只替换专家实现和标签适配器。

必须测试：

- [ ] 前景固定、背景随机替换。
- [ ] 冲突背景。
- [ ] 清晰和模糊对象。
- [ ] 上下文插件缺失或错误。
- [ ] 无关插件接入。

### 单元测试

- [ ] 接口字段范围。

- [ ] 约束投影。
- [ ] 缺失插件。

- [ ] 第二场景无需修改核心代码。
- [ ] 性能—成本曲线满足预设预算。

# 第二部分：双机器人通信协同系统

## 12. 推荐技术栈

首版架构不是“最高决策者控制两个机器人”，而是**车队任务协调器/监督器负责任务级意图，本地机器人负责实时执行与安全自治**。中央只能提出任务目标和资源约束；机器人本地`command_gate`与安全监督器拥有最终接受、拒绝、暂停和急停权。集中式调度本身是工程选型，不作为论文或专利创新点。

首版建议：

- [ ] ROS Noetic（ROS1）作为机器人中间件基线。
- [ ] Ubuntu 20.04和ROS Noetic依赖版本固定；ROS Noetic已于2025-05-31 EOL。
- [ ] `roscpp`实现高频、低延迟或安全相关节点，`rospy`实现编排、监控和非实时工具。
- [ ] ROS1 topics传递状态与事件，services执行短时查询/命令，`actionlib`执行可反馈、可取消的长任务。
- [ ] Gazebo或等价仿真器；只选一种主仿真环境。
- [ ] `move_base`或现有ROS1导航栈负责本地规划和控制。
- [ ] `rosbag`用于消息录制和回放。
- [ ] `diagnostic_msgs`/`diagnostic_updater`发布健康状态。
- [ ] `bond`或显式heartbeat topic检测节点和机器人失联。
- [ ] `dynamic_reconfigure`调整允许运行时变化的阈值并记录变更。
- [ ] `roslaunch`的`respawn`、systemd或等价supervisor管理节点启动和恢复。
- [ ] 行为树或显式状态机实现任务协调；首版不使用端到端MARL。
- [ ] 网络故障注入工具模拟延迟、丢包、乱序和断网。

ROS1没有ROS2/DDS的QoS与Lifecycle语义。可靠性必须由应用层ACK、`seq`、TTL、重试、去重和本地安全回退实现，不能把TCPROS连接等同于业务处理成功。

### ROS Noetic EOL风险

- [ ] 建立可复现容器或系统镜像并固定apt、rosdep和源码依赖。
- [ ] 建立内部包缓存或归档，避免上游资源变化阻断构建。
- [ ] 团队自行承担安全补丁、依赖兼容和系统维护。
- [ ] 限制ROS Master和节点XML-RPC/TCPROS端口的网络暴露。
- [ ] 将ROS2或其他受支持中间件迁移作为独立技术债。

### 首版单roscore、单车队监督器拓扑

```text
              +------------------------+
              |  roscore / ROS Master  |
              +-----------+------------+
                          |
              +-----------+------------+
              | fleet_supervisor       |
              | state_aggregator       |
              | task/resource leases   |
              +-----+-------------+----+
                    |             |
             TaskCommand     TaskCommand
                    |             |
          /robot_1 namespace  /robot_2 namespace
          command_gate         command_gate
          local executive      local executive
          local safety         local safety
```

- [ ] 两机器人统一设置`ROS_MASTER_URI`。
- [ ] 每台机器人设置对方可访问的`ROS_IP`或`ROS_HOSTNAME`。
- [ ] 使用`/robot_1`、`/robot_2`命名空间隔离同名资源。
- [ ] 通过chrony/NTP同步真机时间；仿真统一使用`/clock`和`use_sim_time`。
- [ ] ROS Master仅负责注册、发现和参数服务；节点数据通常经TCPROS/UDPROS点对点传输。
- [ ] Master失效后既有连接可能暂时存在，但新注册、发现、service查询和参数访问会失败，不依赖其必然持续。
- [ ] 本地安全、局部规划和急停必须在Master失效时继续运行。
- [ ] 首版只有一个业务核心；使用systemd/`roslaunch respawn`恢复，重启时递增持久化`epoch`。
- [ ] 首版不做热备或双活，避免尚未建立quorum和fencing时产生分裂脑。

### 节点职责

- [ ] `communication_gateway`：序列号、TTL、ACK、重试、去重和版本。
- [ ] `state_aggregator`：按`boot_id/seq`接收状态摘要，计算新鲜度并生成带`snapshot_id`的车队快照。
- [ ] `fleet_supervisor`：基于快照、任务目标和异常执行任务级分配、取消、等待与重规划。
- [ ] `resource_lease_manager`：管理任务租约和狭窄通道、工位等排他资源租约。
- [ ] `command_gate`：每台机器人本地校验`epoch/command_id/valid_until`、资源租约、能力和安全前置条件。
- [ ] `task_manager`：在本地执行认领、进度、阻塞、完成和交接状态机。
- [ ] `anomaly_manager`：环境、目标、健康和通信异常生命周期。
- [ ] `shared_world_model`：来源保留的地图、目标和事件状态。
- [ ] `mission_coordinator`：保留为`fleet_supervisor`内部策略模块或兼容别名，不形成第二个命令权威。
- [ ] `safety_supervisor`：每台机器人本地急停、避障、限速和降级；其否决优先级高于中央命令。
- [ ] `perception_adapter`：把视觉输出转换成目标观测和异常。
- [ ] `network_monitor`：链路质量、延迟、丢包和失联。
- [ ] `recorder`：日志、指标和可回放事件。

### 权限边界

中央应接收状态摘要、异常、任务目标、能力、地图/资源约束和操作员任务级指令；应输出声明式任务Goal、Cancel、Hold、Return和资源租约。中央不得直接发布`cmd_vel`、关节实时控制、急停复位或安全旁路。原始图像/点云不应以“汇总所有状态”为由持续上传；需要时通过证据URI或按需请求获取。

## 14. ROS1接口示例

### RobotStatus

```text
std_msgs/Header header
string protocol_version
string mission_id
string robot_id
string boot_id
uint64 sequence_number
uint8 operating_mode
geometry_msgs/PoseWithCovariance pose
geometry_msgs/TwistWithCovariance twist
float32 battery_percent
float32 localization_quality
string current_task_id
string current_command_id
uint8 task_state
uint8 local_safety_state
string map_version
time valid_until
```

`header.stamp`是源时间；状态聚合器另记本地接收单调时间。`boot_id`在机器人/状态发布进程每次启动时改变，`sequence_number`只在同一`boot_id`内比较。

### FleetSnapshot

```text
std_msgs/Header header
string snapshot_id
uint64 epoch
RobotStatus[] robot_states
duration[] state_ages
uint8[] freshness       # fresh, degraded, stale, lost
string map_version
```

- [ ] 快照必须记录每台机器人的数据年龄和质量，不把缺失状态填成“正常”。
- [ ] 依赖精确相对状态的任务不得使用`stale/lost`数据。
- [ ] 建议初始阈值：状态10 Hz；0.5 s内新鲜、0.5–1.5 s降级、超过1.5 s陈旧、超过3 s失联，之后按制动距离和网络实测调整。

关键枚举必须由共享接口包定义，不能由机器人各自解释。

### services与actionlib

- [ ] `QuerySharedState.srv`仅用于短时快照查询。
- [ ] `ResolveConflict.srv`仅提交或查询冲突决议，不承载长时工作流。
- [ ] `HandoffTask.action`用于任务交接，提供反馈、取消和结果。
- [ ] `TaskCommand.action`用于中央下发任务级命令；Goal必须含`epoch`、`command_id`、`snapshot_id`、`issued_at`、`not_before`、`valid_until`、`lease_duration`、任务参数、前置条件、`resource_lease_ids`、`supersedes_command_id`和`partition_policy`。
- [ ] Result至少区分`ACCEPTED`、`REJECTED`、`DUPLICATE`、`STALE_EPOCH`、`EXPIRED`、`COMPLETED`和原因码。
- [ ] `command_id`全局唯一；相同ID的重试返回既有状态/结果，不重复执行有副作用操作。
- [ ] service调用失败必须有超时和降级，不阻塞本地安全线程。

### epoch、租约与本地command gate

- [ ] `fleet_supervisor`每次启动从本地持久化计数器原子递增`epoch`；机器人持久化已接受的最高epoch。
- [ ] 低于最高epoch、已过`valid_until`、尚未到`not_before`或前置条件不成立的命令必须被拒绝。
- [ ] 任务租约定义中央任务权限的有效期，资源租约定义排他资源占用；两者都不能靠ROS连接状态隐式维持。
- [ ] 机器人以校正后的`valid_until`与“本地接收单调时钟 + `lease_duration`”中更早者作为保守到期时刻；时钟同步质量不足时不得延长租约。
- [ ] 旧资源租约到期后，还需等待最大时钟偏差和网络裕量，中央才能重新分配同一资源。
- [ ] 命令topic/action不得latched，避免机器人重连后自动收到旧命令。
- [ ] 本地`command_gate`通过后只把任务Goal交给local executive；`safety_supervisor/cmd_vel_mux`仍可随时限速、停止或拒绝。
- [ ] 建议核心循环2–5 Hz、状态10 Hz、本地安全20–50 Hz；中央循环不得承担碰撞反应时限。

## 15. ROS1 Topic与应用层可靠性

| Topic | 频率/触发 | ROS1机制 | 说明 |
|---|---|---|---|
| `/robot_i/fleet_state` | 10 Hz建议值 | TCPROS，`queue_size=1` | 含`boot_id/seq`；新状态替代旧状态 |
| `/fleet/snapshot` | 2–5 Hz/事件 | TCPROS，小队列 | 监控与审计用，含`snapshot_id`和新鲜度 |
| `/fleet/core_heartbeat` | 周期 | TCPROS，小队列或`bond` | 含`epoch`和核心身份；不用作安全控制 |
| `/robot_i/task_command/*` | 事件/actionlib | TCPROS + Goal/Feedback/Result | Goal含epoch、租约和幂等ID |
| `/robot_i/command_ack` | 事件 | TCPROS + command_id | 接收、拒绝、重复、过期和完成结果 |
| `/fleet/task_events` | 事件 | TCPROS + 应用ACK/重试/去重 | 任务事件不可静默丢失 |
| `/fleet/anomalies` | 事件 | TCPROS + 应用ACK/重试/去重 | 关键异常需处理确认 |
| `/fleet/target_observations` | 事件/低频 | TCPROS + seq/TTL | 保留来源和时间 |
| `/fleet/map_delta` | 按需 | TCPROS、限流和版本 | 不持续广播整图 |
| `/fleet/ack` | 事件 | TCPROS + correlation_id | 关联原消息ID |

### 可靠性约束

- [ ] ROS1不提供ROS2/DDS式QoS；文档和代码不得使用“Reliable QoS”等虚假保证。
- [ ] TCPROS提供有序字节流基础，但不证明接收应用已校验或执行消息。
- [ ] 关键消息在应用层携带唯一ID、seq、TTL、重试计数和`requires_ack`。
- [ ] ACK只在接收方完成协议校验并将事件写入状态机后返回。
- [ ] 接收方按消息ID幂等去重，发送方按退避策略重试。
- [ ] 紧急本地动作不等待ACK。
- [ ] 高频状态使用小publisher/subscriber队列，避免陈旧状态堆积。
- [ ] latched topic只用于最新快照或静态信息，不充当事件日志。
- [ ] 任务命令、租约和核心心跳不得使用latched topic。
- [ ] 所有空间数据携带坐标系和观测时间。
- [ ] `dynamic_reconfigure`只改变白名单参数，并把变更记录进审计日志。

## 16. 状态机实现

### 任务状态机

```text
UNASSIGNED
  → CLAIMED
  → IN_PROGRESS
  → COMPLETED

IN_PROGRESS
  → BLOCKED
  → HANDOFF_REQUESTED
  → HANDED_OFF

任意非终态
  → ABORTED
```

每次转换必须：

- [ ] 校验当前状态和事件版本。
- [ ] 校验中央`epoch`、任务租约、资源租约和命令前置条件。
- [ ] 写入事件日志。
- [ ] 以`command_id`和幂等事件ID关联转换；重复命令不得重复产生副作用。
- [ ] 更新本地快照。
- [ ] 必要时等待对方ACK。

### 异常状态机

```text
DETECTED
  → REPORTED
  → ACKNOWLEDGED
  → UNDER_REVIEW
  → CONFIRMED | REJECTED
  → MITIGATING
  → RESOLVED | ESCALATED
```

### 冲突规则

- [ ] 同一排他任务双重请求：由中央按代价、优先级和机器人ID确定性解决，并只签发一个未过期租约。
- [ ] 本地因安全或能力拒绝命令：中央登记原因并重新规划，不得反复强制下发。
- [ ] 目标观测冲突：保留双方来源，触发复查。
- [ ] 地图冲突：不使用最后写入覆盖，保留增量和撤销记录。
- [ ] 坐标变换失败：拒绝融合。
- [ ] 过期事件：归档但不影响当前决策。

## 17. 机器人运行时流程

```text
机器人状态摘要
  ↓
state_aggregator校验boot_id/seq/时间/坐标系
  ↓
FleetSnapshot(snapshot_id + freshness)
  ↓
fleet_supervisor分配任务并申请资源租约
  ↓
TaskCommand(epoch + command_id + valid_until)
  ↓
机器人本地command_gate校验、幂等去重并ACK
  ↓
local executive / move_base
  ↓
本地safety_supervisor与cmd_vel_mux最终裁决
  ↓
反馈、结果、异常、审计与录包
```

### 核心故障与网络分区流程

- [ ] 核心重启：持久epoch递增，从机器人状态和事件日志重建快照；重建完成前只允许`HOLD/STOP`等保守命令。
- [ ] 机器人失去核心：按本地单调时钟等待当前租约到期，然后执行`partition_policy`（安全等待、完成最小原子步骤或前往安全点）。
- [ ] 核心只连通一台机器人：把失联机器人的最后位置和资源占用视为仍有效，直到旧租约加时钟/网络裕量安全到期。
- [ ] 共同搬运、窄道互斥等强耦合任务：任一机器人或核心失联即停止协同动作。
- [ ] 本地急停、避障和设备保护始终执行，不等待核心心跳、ACK或ROS Master。

- [ ] 任意故障注入下不存在两个机器人同时持有同一有效排他资源租约。
- [ ] 命令租约过期后机器人在规定时间内进入预定义本地降级。
- [ ] Master失效时本地安全和局部规划继续运行，协作按设计降级。
- [ ] 本地安全始终独立。
- [ ] 硬件在环趋势与仿真一致。

### R4：带宽优化与学习通信

仅在R3完成后：

- [ ] 建立固定周期和事件触发强基线。
- [ ] 学习发送时机或摘要，不学习安全动作。
- [ ] 训练中随机化链路和机器人故障。
- [ ] 对比相同任务风险下的通信成本。

退出条件：

- [ ] 学习通信显著优于事件触发基线。
- [ ] 不破坏协议、状态机和安全回退。

## 20.1 ROS1拓扑升级边界

首版单`roscore`通过R0—R3后，才评估：

### Active-passive备份核心

- [ ] 首版明确不做热备；先验证单核心进程重启、持久epoch和本地安全降级。
- [ ] 后续active-passive使用奇数仲裁节点或外部一致性存储形成quorum；只有quorum侧可以产生leader。
- [ ] leader持有短期`leader lease`并获得单调递增`epoch`作为fencing token。
- [ ] standby只复制快照、任务、命令结果和租约日志，不发布TaskCommand。
- [ ] 机器人仅接受最高epoch且leader lease有效的命令；无quorum时不接受新任务/资源租约。
- [ ] 切换后用`command_id`恢复幂等结果；禁止两个核心同时发布后让机器人按到达顺序选择。

### 多主

- [ ] 可评估`multimaster_fkie`等ROS1多主方案。
- [ ] 明确发现同步、命名冲突、重复转发、网络分区和恢复语义。
- [ ] 多主不替代任务仲裁、消息去重和本地安全。
- [ ] ROS Master多主不等于业务核心高可用，不能替代quorum、leader lease和fencing。

### 应用层桥接

- [ ] 每个机器人运行本地`roscore`。
- [ ] 专用gateway只桥接白名单任务、异常、目标和地图增量。
- [ ] gateway继续使用现有消息ID、seq、TTL、ACK、重试和去重。
- [ ] 不透明镜像整个ROS图。
- [ ] 桥接传输可独立选择TCP、ZeroMQ、gRPC等，但需单独验证。

### ROS2迁移

- [ ] 长期维护、安全、复杂QoS或更大规模部署需求出现时，单独评估ROS2迁移。
- [ ] ROS2迁移不与当前算法验证混在同一阶段。

### 分布式或分层升级

- [ ] 机器人数量、分区频率或中央带宽成为瓶颈后，再评估CBBA/C-ADMM等分布式任务分配。
- [ ] 编队、避碰和相对控制保持本地/邻居闭环，中央只发队形参考和任务约束。
- [ ] 分区子协调器必须明确跨区排他资源的唯一租约权威。
- [ ] 任何升级都保留本地安全否决、epoch fencing、命令幂等和租约过期语义。

## 20.2 技术贡献边界

- [ ] 普通的中央状态汇总、任务分配和ROS topic通信属于常规架构，不单独表述为论文创新。
- [ ] 论文候选聚焦可验证的“任务权限安全降级”：状态新鲜度、快照一致性、任务/资源租约、epoch fencing、本地安全门与分区恢复的形式化语义和故障实验。
- [ ] 专利候选应落到上述模块如何联动、怎样避免旧命令复活和资源双重占用、怎样触发本地安全回退的具体技术流程；不以“最高决策核心”作宽泛技术点。
- [ ] 以上是研发成果组织建议，不构成法律结论；公开前另行完成现有技术检索和披露顺序决策。

# 第三部分：两系统集成

## 21. 集成边界

视觉系统通过稳定服务或进程内适配器向机器人发布：

```text
target_class
target_pose
support_evidence
contradiction_evidence
uncertainty
quality
applicability
model_version
evidence_uri
```

机器人侧只接收任务级结果，不直接访问视觉专家内部状态。

### 集成规则

- [ ] 视觉输出先经过机器人侧`perception_adapter`。
- [ ] 低质量或高不确定结果生成复查请求，不生成确定目标事件。
- [ ] 视觉模型版本变化必须记录。
- [ ] 两机器人视觉判断冲突进入目标异常状态机。
- [ ] 紧急避障不得依赖远端视觉融合。

## 22. 联合集成顺序

1. [ ] 视觉系统离线稳定并导出固定接口。
2. [ ] 机器人系统使用模拟视觉消息完成P0/P1。
3. [ ] 接入单机器人真实视觉输出。
4. [ ] 验证视觉异常和拒识能够触发正确任务逻辑。
5. [ ] 接入双机器人目标观测。
6. [ ] 测试目标冲突、丢失、重复和复查。
7. [ ] 最后测试额外模态调用和跨机器人协助。

## 23. 共同止损条件

- [ ] 视觉输出尚未校准时，不用于自动任务交接。
- [ ] 机器人协议不稳定时，不引入学习通信。
- [ ] 共享目标状态错误传播风险高于收益时，退回“通知+人工确认”。
- [ ] 联合系统无法区分感知错误和通信错误时，先完善审计链路。
- [ ] 任一模块升级破坏回放兼容性时，暂停部署。
